# 资料稀疏时的需求补全与现场落地

很多项目只有现场照片、客户口头描述、设备清单或几条想法。此时不能把缺失内容当成已确认需求，也不能因为资料少就只写产品介绍。应使用“证据提取 -> 方案假设 -> 待确认 -> 可落地设计”的闭环。

## 一、资料分层

把输入分为四类，并在内部台账中保留来源：

| 资料类别 | 可直接写入 | 需要补充或确认 |
|---|---|---|
| 客户明确要求 | 项目范围、已点名模块、明确页面/功能、明确接口或部署约束 | 口头要求中的数量、性能、边界和责任 |
| 现场照片/视频 | 可见设备、工位相对位置、空间约束、线缆/气源迹象、屏幕安装位置、人员操作姿态 | 不可见的尺寸、内部结构、协议、精度、节拍和安全等级 |
| 既有技术方案/产品资料 | 通用功能、可选架构、常见章节、候选设备和验收思路 | 当前项目是否采用、具体参数、兼容性和效果 |
| 设计推断 | 只可写为“建议/假设/待确认” | 不得直接变成承诺、报价依据或验收指标 |

现场照片要逐张编号，例如 `P-01`、`P-02`，记录拍摄位置、方向、可见事实、推断、影响章节和需补拍内容。照片只证明“看得到的状态”，不证明性能、协议或质量结果。

## 二、从口头想法转为可执行需求

将“想要装配系统”“要上大屏”“扳手联网”“希望防错”等说法转换为：

`对象 | 场景 | 触发 | 输入 | 处理规则 | 输出 | 异常 | 责任方 | 验收证据`

例如“扳手联网”至少拆成工具身份、连接方式、参数下发、结果回传、断线策略、离线缓存、重复消息、校准有效期和工具换工位控制；“要大屏”至少拆成受众、页面、数据源、指标口径、刷新周期、异常闭环和屏幕/网络条件。

## 三、以客户点名模块为主线

用户明确说出模块时，模块清单是方案范围的第一约束。例如“装配系统 + 大屏 + 扳手”应装配：

1. 装配系统：工件/工单、工艺、工步、人员、工具绑定、作业引导、防错、结果、曲线、追溯和外部接口。
2. 智能扳手：工具身份、通信、参数下发、结果回传、校准状态、离线与补传。
3. 大屏：数据源、指标口径、页面、刷新、异常、权限、部署和断流提示。
4. 跨模块闭环：装配系统产生业务状态，扳手产生原始拧紧结果，大屏消费归一后的业务状态；三者用工件/工单/工位/工步/工具等明确身份键关联。

未被用户点名的拧紧机、校验台、数字孪生或信创内容，只能作为“可选建议/待确认”，不能自动写成采购范围。若现场照片显示可能存在相关设备，应列为现场发现，不得擅自扩大范围。

## 四、用以往方案补全但不照搬

参考历史方案时，先抽取可复用的“设计模式”：

- 章节：背景、现状、目标、边界、架构、设备、软件、接口、实施、验收。
- 功能：工艺版本、工步防错、结果追溯、工具管理、异常闭环、报表和权限。
- 接口：工单/工艺下发、设备结果回传、状态上报、附件和失败补传。
- 验收：正常、错误、断网、断电、重复提交、工具过期、权限和数据一致性。

然后把历史内容改写为当前项目的候选设计，并标记 `来源=历史参考`、`状态=建议/待确认`。不得复制原客户名称、现场尺寸、品牌参数、价格、工期、效果数字或未经确认的接口字段。

## 五、现场照片到实际落地

每张照片至少形成一条“观察 -> 影响 -> 设计动作 -> 验证动作”：

- 看到工位狭窄、人员绕行：提出工具可达性、PDA 支架、AP 覆盖、线缆和安全距离核查；要求补测尺寸并做现场走位确认。
- 看到已有显示屏或控制柜：核对屏幕尺寸、输入信号、网络、电源、数据来源和是否复用；形成接入或替换方案。
- 看到扳手/充电柜/扫码器：登记设备数量和摆放，核对协议、工具 ID、校准状态、电池和充电位置；安排通信联调和工具盘点。
- 看到车辆/工件流转区域：绘制工位、工件 ID、开工/完工节点和异常隔离区；让客户确认业务流程和责任人。

不能从照片直接得出扭矩精度、节拍、网络质量、协议、设备内部配置或安全合规结论；这些必须通过测量、资料或现场测试确认。

## 六、建议输出的中间成果

资料不足时，先生成内部三张表，再写正式方案：

1. **现场证据表**：照片编号/口头原话/文件来源、可见事实、推断、影响、需补证据。
2. **模块装配表**：客户明确模块、建议补充模块、暂不纳入模块、模块接口和责任边界。
3. **落地问题表**：问题、为什么影响设计、需要谁确认、确认方式、截止阶段、未确认时的保守设计。

正式方案中可保留“现状依据”和“待确认项”，但不把内部推理过程、未经客户确认的替代方案和资料缺口伪装成定案。
