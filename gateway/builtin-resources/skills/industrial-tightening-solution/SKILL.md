# Industrial Tightening Solution

用于检索、编写、评审或拆解“拧紧设备 + 现场作业 + 工业软件 + 数据追溯”的技术方案、技术协议、投标响应、汇报 PPT 或验收材料。核心工作不是套目录，而是先从公开同类方案、产品资料、标准和招标文件中提炼本项目应写清的边界与证据。

本 Skill 本身只保存通用方法、模块结构、写作规则和验收思路，不固化任何客户名称、公司名称、项目名称、联系人、地址、价格或专属参数。具体名称只在用户明确要求编写当前项目成稿时进入该项目交付物，不回写到 Skill 或通用参考文件。

- 拧紧轴、伺服拧紧机、多轴/同步拧紧、机器人拧紧和专用工装。
- 智能电动扳手、数显扭矩扳手、手动/电动工具联网和工具管理。
- 扭矩校验台、扭矩检定仪、传感器、自动加力、校准证书和校验追溯。
- 生产大屏、车间布局、工位/计划/异常/安全/设备/精益改善等现场管理。
- MES/MOM/KMIS/LIMS/PLM 等接口，数据库、Web/PC/PDA/平板和报表。
- 数字孪生、三维工位/车辆/设备可视化、实时状态映射和历史回放。
- 信创或国产化环境的服务器、操作系统、数据库、中间件、浏览器和适配验证。

## 先判断交付物

根据用户要的是以下哪一种来组织内容，不要把产品介绍写成项目技术协议：

1. **产品/能力介绍**：突出设备族、适用场景、关键能力和案例；参数必须标注来源或待确认。
2. **项目技术方案**：按现状痛点 -> 目标 -> 工艺/设备 -> 软件/接口 -> 实施 -> 验收闭环。
3. **技术协议/招标响应**：将“必须满足、可选、甲方提供、待澄清”分开，逐条形成响应矩阵。
4. **汇报 PPT/大屏方案**：面向决策者先讲价值和现场流程，再展示架构、页面和落地计划；避免堆砌产品参数。
5. **评审/审查**：检查数据流、设备状态、协议边界、异常恢复、指标可测性和验收证据，不因文档写了某项功能就判定已实现。

## 公开资料研究

当用户问“网上有没有类似方案”“应该怎么写”或要求借鉴行业方案时，先检索公开资料，再写方案。读取 [proposal-writing.md](references/proposal-writing.md)。

- 优先顺序：国家/行业标准与客户公开招标文件 -> 原厂技术手册和白皮书 -> 可核验的项目案例 -> 行业媒体/集成商文章。
- 搜索要按场景组合关键词，例如“铁路 轴端 螺栓 智能拧紧 技术方案”“扭矩校验台 技术规格书”“制造执行 生产大屏 解决方案”“工业数字孪生 车间 技术方案”“信创 智能制造 部署 方案”。
- 每一项外部信息记录来源、发布日期、适用对象、原始措辞与可复用结论；无法核验的网页、营销口号和案例效果只能作为灵感，不能写成技术承诺。
- 公开资料用于形成“应包含哪些章节/功能/验收点”，不复制客户名、商业价格、专利、实现细节或效果数字。

## 直接套用完整模板

用户已经提供项目资料、设备清单或技术协议时，可以直接进入“模板填充模式”，读取 [proposal-template.md](references/proposal-template.md)。资料只有现场照片、口头想法或少量清单时，同时读取 [sparse-input-and-photo.md](references/sparse-input-and-photo.md)：

1. 先提取用户明确点名的模块、项目事实、客户要求、参考资料和待确认项，并读取 [solution-profiles.md](references/solution-profiles.md) 为每个模块选择写作 Profile；不要把 A-D 当成固定组合类型。
2. 现场照片按编号提取可见事实、空间/设备/网络线索和补拍需求；口头想法转换为可验收的对象、触发、输入、处理、输出、异常和责任方。
3. 内部母版保持完整以便检查；客户版按实际模块装配章节，删除不适用专题。只有逐条招标响应或客户固定目录要求时，才保留不适用章节并标记“不适用/无偏离”。
4. 对每个空缺字段写“待确认”，同时生成问题清单；不得用网上常见参数补齐客户专属要求。
5. 将参考资料中的内容标记为“参考方案/来源”，将当前项目承诺标记为“本项目方案”；两者不能混写。
6. 输出前生成“需求 -> 章节 -> 设备/软件 -> 验收条款”的追踪表和“假设/风险/待澄清”清单。

用户只要说“按完整模板直接写”，就不必再次询问目录；只在缺失信息会改变设备选型、架构、价格、工期或验收结论时提问。

例如用户说“本项目是装配系统 + 大屏 + 扳手”，应以这三个模块为范围主线：补齐人员/工件/工单/工艺/工步、扳手通信与结果追溯、大屏指标与数据链路，再根据现场照片补充工位布置、网络、电源、PDA 支架、工具存放和联调动作。拧紧机、校验台、数字孪生或信创只有在用户提出、资料明确或列为待确认建议时出现，不得自动写成采购范围。

## 推荐输入

缺少信息时列为“待澄清”，不要擅自补值。优先收集：客户行业/工厂、车型或产品、工位和工序、螺栓数量与规格、扭矩/角度范围、节拍、空间和电源/气源、工具品牌及协议、校准等级、现有 MES/MOM/KMIS/LIMS、网络隔离、国产化要求、用户角色、数据保留期、交付边界和验收方式。

## 方案工作流

1. 建立需求和证据表：把每个需求映射到设备、软件模块、接口、测试和验收条款。
2. 读取 [solution-profiles.md](references/solution-profiles.md)，根据用户明确模块选择一个或多个模块 Profile；模块组合可以任意，不能只从固定套餐中选择。
3. 资料稀疏时读取 [sparse-input-and-photo.md](references/sparse-input-and-photo.md)，用现场证据和历史方案补齐设计问题，但将推断标记为建议/假设/待确认。
4. 先画边界和数据流：每个模块有独立闭环，跨模块用唯一身份键、数据所有权和失败恢复连接。
5. 需要行业参考时，先按“公开资料研究”检索并形成来源台账；只将已核验结论写入方案。
6. 选择需要的模块，读取 [solution-modules.md](references/solution-modules.md)；涉及数字孪生或信创时再读取 [twin-and-xinchuang.md](references/twin-and-xinchuang.md)。
7. 按交付物和实际模块装配章节，读取 [proposal-writing.md](references/proposal-writing.md)；用户要求直接成稿时再读取 [proposal-template.md](references/proposal-template.md)。
8. 写设备与软件方案，明确控制闭环、状态机、通信协议、权限、审计、超时、重试、离线和恢复行为。组合项目必须额外检查身份键、数据所有权、跨模块时序、幂等和失败恢复。
9. 写实施、培训、试运行、运维、备件、质保和回滚边界，并把照片中的空间、网络、电源、设备和人员操作线索转成测量、布置、安装和联调动作。
10. 写可执行验收矩阵，读取 [acceptance-and-evidence.md](references/acceptance-and-evidence.md)。将各模块单项验收、跨模块端到端验收、静态文档、仿真、host test、现场联调、客户验收和硬件实测分开。
11. 输出 PPT、DOCX、PDF 或技术协议时，沿用对应 artifact skill 的渲染与检查流程；不要把方案草稿、内部推测或生成过程写入受众可见内容。

## 不变量与风险边界

- 扭矩、角度、速度、精度、节拍、MTBF、一次合格率等数字必须有来源、测试条件和适用范围；参考文件中的数字不能自动成为新项目承诺。
- 参数要注明单位、容差、量程、采样/判定方式和边界条件。扭矩校验与现场拧紧结果不能混为同一精度指标。
- 工具/拧紧轴适配必须说明协议、连接方式、设备身份、结果回传、断线重连、重复回调和离线缓存；不能只写“支持接口”。
- 质量判定必须覆盖漏拧、重拧、欠拧、超拧、错序、错工位、重复提交、校验过期、传感器异常和人工放行审计。
- 网络、串口、设备和数据库操作应有 timeout/cancellation、资源释放和明确失败状态；UI 不执行 blocking IO。
- 信创是部署与适配约束，不是“国产化”口号。必须列出目标软硬件组合、替代组件、兼容性测试、密码/证书、数据迁移、性能和回退方案。
- 数字孪生只在有资产、坐标、状态源、刷新周期和一致性定义时承诺；没有真实三维模型或遥测源时使用“预留/可扩展”，不伪造实时孪生效果。
- 不从参考方案复制客户名称、联系人、价格、专利、案例效果或未验证的百分比；这些内容必须由当前项目证据重新确认。
