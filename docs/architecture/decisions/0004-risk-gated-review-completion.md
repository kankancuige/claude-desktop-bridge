# ADR 0004：风险门禁审查与父任务完成协调

Checklist: 25/25 complete
Incomplete: None

**Status:** Accepted
**Date:** 2026-08-13
**Owner:** Claude Desktop Bridge maintainer

## Context

当前主会话收到 SDK `result` 后立即持久化成功、生成桌面完成气泡并向 IM 镜像结果，Power 最终审查则在之后异步运行。Workflow 的 `done` 只表示脚本运行结束，审查结果没有参与父任务终态，也没有发现问题后的修复闭环。另一方面，普通修改也被分配 Balanced 最终审查，容易为低风险任务增加不必要的模型调用和等待时间。

## Drivers

- 微信、飞书和钉钉只能在整个任务真实完成后收到完成通知。
- 低风险任务不应为形式化审查支付额外 latency、token 和失败面。
- 高风险变更必须经过独立只读复核，且审查发现阻断问题后不能宣称成功。
- 主会话是唯一写入者；审查 Agent 只读，避免并行修改和工作区竞态。
- 状态必须可持久化、可恢复、幂等，并能区分执行结束、审查中、需要修复和最终完成。
- 自动闭环必须有明确上限，避免审查与修复无限循环。

## Options

1. 保持主 `result` 即完成，仅修正桌面文案：改动最小，但持久化和 IM 仍会提前成功，审查仍无门禁作用。
2. 所有代码修改统一执行完整 Power 审查：语义简单，但低风险任务成本和耗时过高，并放大模型不可用造成的阻塞。
3. Gateway 建立父任务协调器，按任务风险和真实差异选择审查深度，并让结构化审查结果驱动后续修复或终态：状态准确、成本可控，但需要统一事件和持久化契约。

## Decision

采用方案 3。Gateway 是父任务完成状态的唯一所有者。SDK `result` 只结算主执行结果；若存在必需审查，父任务进入 `reviewing`，桌面端和 IM 不得自行推断成功。只有协调器产生一次 `task_completed`，才能显示成功、清理队列和发送最终 IM 回复。

审查策略按任务决策与真实 checkpoint 差异取较高风险：

- `low` 或无真实文件差异：跳过 Agent 审查，依赖已执行的确定性 build/test，直接完成。
- `medium`：运行一个 Balanced 定向审查，只覆盖 correctness、异常路径、状态一致性和本次变更契约；不运行完整性评论、性能泛扫或报告汇总 Agent。
- `high/critical`：运行 Power 门禁审查；仅对命中的风险域启用维度，关键发现再做一次证伪，不机械执行固定数量的全维度 Agent。
- 用户明确要求全面审计时，继续使用独立 `audit-sweep`，它不等同于每次实现后的最终门禁。

最终审查必须返回结构化 `ReviewOutcome`，至少包含 `passed`、`blockingFindings`、`advisoryFindings`、`summary` 和 `tier`。`workflow_done` 不等于审查通过。

若第一次最终审查存在 `critical/high`，或明确标记 `blocking=true` 的真实问题，协调器进入 `changes_required`，将脱敏且有界的结构化发现作为内部用户消息回灌主会话，由主会话继续修复。自动修复最多一次，修复后最多自动复核一次。复核仍有阻断问题、审查失败、审查暂停、Power 模型不可用或无法恢复时，父任务进入可恢复的非成功终态并等待用户处理，不再自动循环。

审查的 `medium/low` 建议项默认不阻止完成，但在最终摘要中展示。用户显式要求“零问题”或项目规则把某类问题定义为阻断时，可通过未来配置提升门槛；本 ADR 不增加新设置项。

协调器持久化当前阶段、主结果、必需子任务、审查轮次、阻断发现摘要、是否已回灌修复、完成事件和通知幂等标记。Gateway 重启后，未完成的 `reviewing/changes_required` 恢复为可继续状态，不得恢复为成功。

## Consequences

- 正面：桌面状态、Agent 面板、持久化和 IM 通知共享同一完成语义；审查真正成为风险门禁；普通任务减少不必要 Agent 调用。
- 正面：审查发现真实问题后有自动修复闭环，不再只生成报告后停止。
- 负面：高风险任务的完成时间包含审查和可能的一次修复复核；协调器需要处理更多中间状态。
- 负面：审查结果结构化失败时必须保守停在非成功状态，不能降级后宣称完成。
- 中性：确定性 build/test 仍由主执行流程完成，审查模型不替代工具验证。
- 兼容：保留现有 `result` 事件用于渲染每个 SDK 回合的统计，但新增父任务状态事件决定最终成功；旧客户端可能继续提前显示，升级桌面端后生效。

## Validation

- 主结果成功且审查运行中时，持久化和客户端状态均为 `reviewing`，没有完成事件或 IM 通知。
- 低风险或无差异任务不启动 Agent 审查。
- 中风险只启动一个 Balanced 定向审查，高风险才启动 Power 门禁。
- 审查通过只完成一次；重复 `workflow_done` 不重复完成或通知。
- 审查发现阻断问题时只自动回灌一次；修复后只复核一次。
- 第二次仍存在阻断问题、审查暂停或失败时不成功，并保留可执行错误提示。
- Gateway 重启后恢复审查/待修复状态，不把中间状态归类为已完成。
- Desktop、微信、飞书和钉钉只消费最终协调事件产生完成提示。

## Review Triggers

- 审查误报率或自动修复失败率持续偏高。
- 平均完成 latency 或 Power token 成本超过产品预算。
- SDK 提供原生父任务/子任务完成树或可恢复 Workflow 契约。
- 产品需要用户可配置阻断严重级别、最大修复轮次或关闭自动修复。
